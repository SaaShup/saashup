Profile and Template: the two core concepts

A Profile (menu "Profiles") is the connection to a NetBox / PaaSBox: think of it as a manageable datacenter. It holds the NetBox URL, the token, and the options describing how that datacenter should be driven.

Saashup is the brain: given a profile, it can automate operations (create, upgrade, operate, delete, refresh hosts…) against the datacenter attached to it.

A Template (menu "Template") is an image ready to be instantiated: Docker image, version, network, ports, volumes, environment variables, etc. It can be created in two ways:

  • by filling in the fields of the Template form directly;
  • by importing a docker run command or a docker-compose.yml file — if the compose file describes several services, one template is created automatically for each of them.

What the Run / Compose import supports

Both importers are simple, best-effort parsers: anything they don't recognize is silently dropped — no error, no warning — so always review the generated template before saving it.

Docker run import reads: the image and tag, --name, --network/--net, -e/--env, -l/--label, -v/--volume and --mount (bind mounts and named volumes), --log-driver/--log-opt. Only the first -p/--publish flag is kept if there are several. Everything else (--restart, --hostname, --user, --workdir, --entrypoint, --pull, --env-file, --add-host, --dns, and any other flag) is read but has no effect on the template.

Docker Compose import reads, per service: image, container_name, networks (name of the first network only), environment/env, labels, ports, volumes (bind and named volumes, short syntax) and logging. One template is created per service, in the order they appear in the file, and that order is also what the Workflow feature replays.

The following are not supported and are always ignored: depends_on (including condition: such as service_completed_successfully — there is no "run once before the others" / migration-style ordering), healthcheck, top-level networks: definitions (so a network's internal: true or any other network-level option is never read, only the network name used in a service), and top-level volumes: definitions (so external: true has no special handling — an external volume is imported the same as any other named volume, just its name and mount path). Private registry images (e.g. ghcr.io/org/image:tag) are parsed correctly as the image reference, but registry credentials are never part of the import — they are configured separately, at the PaaSBox/NetBox host level.

Once a profile and at least one template are ready, the operations (Create, Upgrade, Operate, Delete…) become available for that profile/template pair.

The profile tag

The tag set on the profile (field "tag") must be present on the Docker hosts on the PaaSBox / NetBox side. It is used to scope exactly which machines this application should be managed on: that same tag is what selects the hosts during upgrades and determines the order in which instances are created.

Branding

A profile can be attached to a Branding (field "Branding" on the Profiles form, managed from the "Branding" menu), so the customer-facing Order, Enroll and Catalog pages for that profile look like part of the customer's own site rather than a generic Saashup page.

A branding lets you set a logo, a primary and secondary color, a background image, a welcome text, a website link and a footer text. One branding can be reused across several profiles, and combined with the "Hide navigation" embed option described above, it lets a Saashup customer give their own end-users an order experience that fully matches their own style.

Instance creation by customers

Customers don't see the admin console at all — they create their instances from the public Order page, landing on a link for one specific, pre-created template. They don't pick a template, an instance name or a DNS name themselves: the page only asks "Do you want to install an instance?" and, once confirmed, Saashup generates the container name and DNS name automatically and provisions the container on a host of the datacenter covered by the tag of the profile attached to that template.

The "Create" menu in the admin console exposes the full form (template, instance name, DNS name, image, version…) for an admin to create an instance directly, without going through the Order page.

Instance limits

Every template has a max instances limit (field "max_instances" on the Template form). It is the default cap on the number of instances any customer can create from that template.

Once a customer has created their first instance, they appear in the "Customers" menu, where that default can be overridden per user for a given template. When a per-user limit is set, it replaces the template default for that customer only — the rest of your customers keep using the template's default limit.

Setting a limit (template default or per-user override) to 0 blocks any further instance creation for that template right away, even if the customer has no instance yet. It does not remove or stop instances that already exist above the new limit — it only prevents new ones from being created.

Embedding the order link on your own site

Saashup's own customers (the SaaS owner using this console) can let their end-users order an instance directly from their own website. From the "Enroll" page's templates list, click the copy icon ("Copy order button HTML") next to a template to open the order button dialog: it shows a live preview and a ready-to-paste <a> HTML snippet linking to that template's order page (/order?template=<name>), which you can paste into your own site to let visitors order the instance there.

The dialog has a "Hide navigation" option: enabling it adds &navigation=false to the generated link, which hides Saashup's own menu and logo on the order page so it blends in as if it were part of your site. This choice is remembered for the visitor's browser session, so it stays hidden across the order/enroll/catalog pages they visit next, even without the parameter on later links.

Hiding the order page

A profile's "Visible" toggle (in the Profiles form) controls whether that profile shows up on the public order/catalog pages. Turning it off hides the profile — and its templates — from those public pages entirely, so customers can no longer order instances from it themselves; only an admin can still create instances for that profile from the admin console's "Create" menu.

Why redirect URLs matter

When an application logs in through Keycloak (OIDC/SSO), Keycloak only redirects the browser back to an instance's URL after login if that exact URL is listed as an allowed redirect URI on the corresponding Keycloak client. If an instance's URL is missing from that list, login will fail with an error on Keycloak's side (typically something like "Invalid parameter: redirect_uri") even though everything else is correctly configured — the application itself, the instance, and the reverse proxy. In other words: for a customer to be able to log in, the instance's URL must be correct and present among the client's allowed redirect URIs in Keycloak.

Keeping that list in sync by hand for every instance you create or delete is tedious and error prone, so Saashup can automate it.

Keycloak is provided by Saashup

The Keycloak server used for this automation is provided by Saashup. To use it, it must be linked from Paashup: Paashup → Keycloak → Servers. This automation is therefore only available when Paashup is used as the datacenter backing a profile — it is not available when the profile is backed by NetBox.

Keycloak automation via labels

A template can be configured so that Saashup automatically registers the instance's URL as an allowed OIDC redirect (callback) URL — and, on removal, unregisters it — on a Keycloak realm/client. This avoids having to manually edit the Keycloak client configuration every time an instance is created or deleted.

This is driven by Docker labels set on the template (the same place you set Traefik or logging labels):

  • saashup.auth.callback.path — required, it is what triggers the automation (e.g. /api/auth/callback). Without this label, nothing is registered in Keycloak.
  • saashup.auth.realm — the Keycloak realm to register the redirect URI on.
  • saashup.auth.client — the Keycloak client id to update.
  • saashup.auth.postlogout.path — optional, a post-logout redirect path (e.g. /logout) registered alongside the callback.

The instance's public URL is derived from its Traefik router labels (host and path prefix), combined with the callback/post-logout paths above. Saashup registers these URLs in Keycloak when the instance is created, and removes them when the instance is deleted.

Upgrading via the UI

From the "Upgrade" menu, pick the profile, the image and the tag (the new version) to deploy. The old tag ("oldversion") is optional: if you leave it out, every existing version of that image is migrated to the new one, with no need to list them one by one.

Don't forget the registry prefix on the image name when it isn't Docker Hub — for example ghcr.io/org/image for GitHub Container Registry, instead of just org/image which is assumed to be on Docker Hub. If the image comes from a private registry, the credentials to pull it must be configured on PaaSBox first, otherwise the upgrade will fail to pull the new tag.

Once started, the upgrade is applied on every host carrying the profile's tag: on each of them, the new image is pulled, the container is recreated from it, and Saashup waits for the recreated container to be confirmed running before moving on.

Upgrading via webhook

An upgrade can also be triggered through a webhook, for example straight from a CI pipeline (GitHub Actions) when a tag is published. The webhook URL looks like: 

https://your-domain.example/registry-webhook/<config-profile>
https://your-domain.example/registry-webhook/<config-profile>/<template>/<secret>
https://your-domain.example/registry-webhook/<config-profile>?secret=<secret>

As an example, this repo's .github/workflows/publish.yml workflow already triggers an upgrade webhook after every tag publication (a push on a semver tag). It can be adapted to notify several webhooks at once by storing the URLs in a WEBHOOK_URLS secret (one full URL per line) and looping over them when the tag is published: 

# WEBHOOK_URLS secret, one full URL per line:
# https://customer-a.example/registry-webhook/profile-a
# https://customer-b.example/registry-webhook/profile-b/template-b/secret-b

- name: Notify upgrade webhooks
  env:
    WEBHOOK_URLS: ${{ secrets.WEBHOOK_URLS }}
    TAG: ${{ github.ref_name }}
  run: |
    while IFS= read -r url; do
      [ -z "$url" ] && continue
      curl -fsS -X POST "$url" \
        -H "Content-Type: application/json" \
        -d "{\"repository\":{\"repo_name\":\"$IMAGE\"},\"push_data\":{\"tag\":\"v${TAG#v}\"}}"
    done <<< "$WEBHOOK_URLS"
